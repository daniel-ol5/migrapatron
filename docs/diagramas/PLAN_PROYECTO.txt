RESUMEN
-------
MigraPatron IA analiza el diario personal de un paciente con migrana y descubre
que factores se repitieron antes de sus episodios. No diagnostica: encuentra
asociaciones en los datos del propio paciente, las explica con numeros y con
palabras, y prepara un resumen que el paciente lleva a consulta.

================================================================================
01. DECISIONES DE ARRANQUE
================================================================================

Tres decisiones cierran el diseno antes de escribir codigo. Quedan registradas
porque en Ingenieria de la Calidad hay que poder justificar por que el sistema
es asi y no de otra forma.


DECISION 1 - Donde corre el motor de analisis
    ELEGIDO: Backend Python + API REST

    Por que:
      - scikit-learn, mlxtend y pandas son maduros para Apriori y arboles de
        decision. Reimplementarlos en Dart seria trabajo perdido.
      - Corregir o reentrenar el algoritmo no obliga a publicar una version
        nueva de la app en la tienda.
      - Reparte el trabajo de 4 personas en dos frentes paralelos (backend y
        movil) en vez de amontonar a todos en Flutter.

    Que cuesta:
      - Se pierde el "todo local / Edge AI".
      - Se compensa con cache SQLite en el movil: la bitacora se guarda
        offline y se sincroniza despues (HU-19).


DECISION 2 - Base del codigo movil
    ELEGIDO: App propia en Flutter, desde cero

    Por que:
      - La cobertura de pruebas, la deuda tecnica y las metricas de SonarQube
        miden codigo del equipo, no codigo heredado. Para esta materia eso es
        determinante: son las metricas que hay que defender.
      - Sin obligaciones de licencia GPL-3.0, que un fork de Migraine Log
        arrastraria a todo el proyecto.
      - Entender una base de codigo ajena es duro para los dos integrantes de
        nivel inicial; escribir la propia es mas lento pero formativo.

    Que cuesta:
      - Aproximadamente una semana extra de UI. Absorbida dentro del Sprint 1.


DECISION 3 - Cadencia
    ELEGIDO: 3 sprints de 3 semanas (9 semanas)

    Por que:
      - Tres entregables demostrables ante el docente: capturar, analizar,
        explicar.
      - Menos ceremonias que 4 sprints de 2 semanas, mas margen por sprint.

    Que cuesta:
      - No hay Sprint 0. El andamiaje tecnico entra como historia HU-00 dentro
        del Sprint 1.


 !! CORRECCION OBLIGATORIA AL DOCUMENTO ORIGINAL !!

    La propuesta original menciona "Edge AI / procesamiento local" como
    tecnologia emergente. Con backend eso ya no aplica. La tecnologia
    emergente que sostiene el proyecto pasa a ser:

        IA EXPLICABLE (XAI) APLICADA A MINERIA DE PATRONES PERSONALES

    que ademas es la parte realmente novedosa. Hay que corregirlo en el
    documento de la materia antes de entregarlo.


================================================================================
02. EL MODULO NUCLEO
================================================================================

De todo MigraPatron se implementa un solo modulo completo, de extremo a
extremo: el MODULO DE INTELIGENCIA DE PATRONES. Se acompana unicamente de lo
que ese modulo necesita para existir y para poder probarse.


LOS TRES SUBMODULOS DEL NUCLEO
------------------------------

  M1 - CAPTURA ESTRUCTURADA
       Bitacora diaria + registro de episodios.
       Por que es imprescindible: sin datos estructurados y fechados no hay
       mineria posible. Es la materia prima del modulo.

  M2 - MOTOR DE PATRONES
       Apriori, arbol de decision, correlacion temporal, nivel de riesgo.
       Por que es imprescindible: es EL diferencial del proyecto. Un diario
       cualquiera guarda fechas; esto encuentra combinaciones.

  M3 - EXPLICACION Y REPORTE
       Hallazgos en lenguaje natural + resumen clinico.
       Por que es imprescindible: sin explicacion es una caja negra, y una
       caja negra no sirve en salud. Aqui vive la "X" de XAI.


MODULOS DE SOPORTE (minimos, solo lo que el nucleo necesita)
-----------------------------------------------------------

  M0 - ACCESO Y PERFIL    Registro, login JWT, perfil clinico, consentimiento.

  El catalogo de factores y el generador de datos sinteticos NO son un
  modulo funcional: son configuracion (se carga por seed en HU-01) y una
  herramienta interna de pruebas (HU-08). Por eso no tienen casos de uso.


ALCANCE DE LAS 9 SEMANAS
------------------------

  ENTRA:
    [x] Registro, login JWT y perfil clinico con consentimiento explicito
    [x] Bitacora diaria de 11 factores + alimentos disparadores
    [x] Episodios: inicio, fin, EVA 1-10, aura, localizacion, sintomas,
        medicacion, minutos hasta el alivio
    [x] Historial en calendario y edicion de registros
    [x] Motor de analisis con ventana de retraso configurable (0-2 dias)
    [x] Reglas de asociacion con soporte, confianza y lift
    [x] Arbol de decision de profundidad <= 3 traducido a reglas legibles
    [x] Significancia estadistica por factor (chi-cuadrado / Fisher)
    [x] Nivel de riesgo diario: bajo / medio / alto
    [x] Hallazgos explicados con evidencia y nivel de confianza
    [x] Panel de tendencias y resumen clinico exportable
    [x] Cache local SQLite con cola de reintento
    [x] Generador de datasets sinteticos con patron conocido

  NO ENTRA:
    [ ] Cuenta de medico dentro del sistema (el paciente comparte un PDF)
    [ ] Notificaciones push y recordatorios
    [ ] Integracion con wearables, Google Fit o Apple Health
    [ ] Datos de clima, presion barometrica o geolocalizacion
    [ ] Modelo predictivo "va a dolerte manana"
    [ ] Multiples idiomas
    [ ] Modelos federados o entrenamiento con datos de otros pacientes
    [ ] Recomendacion de medicacion o de tratamiento


LIMITE DECLARADO DEL PRODUCTO  (va escrito dentro de la app)
------------------------------------------------------------
  MigraPatron NO diagnostica, NO determina causas y NO recomienda medicacion.
  Muestra asociaciones estadisticas en los datos del propio paciente.

  Toda pantalla de hallazgos lleva de forma permanente la leyenda:

      "Una asociacion no demuestra causalidad.
       Comenta estos resultados con tu medico."

  Esto no es letra chica legal: es un REQUISITO FUNCIONAL VERIFICABLE, con su
  historia de usuario (HU-15) y su caso de prueba.

================================================================================
04. CASOS DE USO Y REQUISITOS
================================================================================

13 casos de uso en 4 paquetes. M1, M2 y M3 son el modulo nucleo; M0 es el
soporte minimo que el nucleo necesita para funcionar.


CRITERIO QUE SE APLICO PARA REDUCIR EL MODELO
---------------------------------------------
Un caso de uso es una META DE UN ACTOR que termina en valor observable, no un
paso interno del sistema. Con ese criterio se eliminaron once casos de uso de
la primera version del modelo:

  Validar suficiencia / Apriori / Arbol de decision / Correlacion temporal
      Los incluia un unico caso de uso (el analisis). Un <<include>> que usa
      un solo caso de uso no es reutilizacion: es DESCOMPOSICION FUNCIONAL,
      el antipatron mas comun en los modelos de casos de uso. Son pasos del
      flujo principal de CU-08 y estan descritos ahi y en la seccion 06.

  Sincronizar registros offline
      El paciente nunca tiene la meta de "sincronizar". Su meta es registrar
      su dia; que eso funcione sin conexion es un ATRIBUTO DE FIABILIDAD.
      Pasa a RNF-04.

  Generar dataset sintetico / Administrar catalogo de factores
      No son funciones del producto: son herramientas internas del equipo. El
      generador vive como historia tecnica HU-08 y el catalogo se carga por
      seed en HU-01. Un actor "Administrador" que no existe en el producto no
      justifica dos casos de uso.

  Editar bitacora / Editar o eliminar episodio / Exportar resumen
      Misma meta que el caso base, distinta pulsacion. Pasan a flujos alternos
      del caso de uso correspondiente.

  Tambien desaparece el actor "Motor de Analisis": esta DENTRO de la frontera
  del sistema, y lo que esta dentro de la frontera no es un actor.

  El resultado es un modelo con 13 casos de uso y UNA sola relacion
  <<extend>>. Que casi no haya relaciones no es una carencia: es la senal de
  que cada caso de uso se sostiene solo.


ACTORES
-------
  PACIENTE          (principal)
      El unico actor que opera el sistema. Registra su bitacora y sus
      episodios, pide el analisis, lee los hallazgos y genera el resumen para
      la consulta.

  MEDICO TRATANTE   (externo, receptor)
      Solo recibe el resumen clinico en PDF que el paciente le comparte.
      NO tiene cuenta ni opera el sistema en este alcance.

CU-08 EN DETALLE - EL CASO DE USO CENTRAL
-----------------------------------------

  Nombre            Analizar mis patrones
  Actor             Paciente
  Modulo            M2 - Analisis de patrones (nucleo)

  Precondicion      Sesion iniciada y consentimiento de analisis aceptado
                    (perfil_clinico.consentimiento_analisis = true).   [RN-01]

  Disparador        El paciente pulsa "Analizar mis patrones", o se cumple el
                    recalculo automatico tras registrar un nuevo episodio.

  FLUJO PRINCIPAL
    1. El sistema lee los registros del periodo (por defecto 90 dias).
    2. Valida que haya al menos 14 dias completos y 3 episodios.       [RN-02]
    3. Construye la matriz uniendo el dia D con el dia D-1 (ventana de
       retraso configurable, lag_dias).
    4. Discretiza cada factor en items segun catalogo_factor y
       regla_discretizacion.
    5. Busca conjuntos frecuentes y genera reglas de asociacion con Apriori,
       conservando solo las que tienen MIGRANA_SI como consecuente.
    6. Entrena un arbol de decision de profundidad <= 3 y traduce cada camino
       raiz-hoja a una regla legible.
    7. Calcula la significancia de cada factor con chi-cuadrado, o test exacto
       de Fisher cuando alguna celda tiene menos de 5 casos.
    8. Filtra por lift, deduplica reglas que se implican entre si y ordena por
       relevancia.                                                     [RN-03]
    9. Compone la explicacion en lenguaje natural de cada hallazgo y le asigna
       su nivel de confianza segun el numero de observaciones.         [RN-04]
   10. Persiste el analisis, sus hallazgos y el riesgo del dia.
   11. Devuelve la lista ordenada al paciente.

    Los pasos 4 a 9 son el motor de patrones. Su funcionamiento interno esta
    detallado en la seccion 06.

  FLUJO ALTERNO A - Datos insuficientes
    En el paso 2, si hay menos de 14 dias completos o menos de 3 episodios:
    guarda el analisis con estado DATOS_INSUFICIENTES, NO muestra ningun
    hallazgo e indica al paciente cuanto le falta registrar.

  FLUJO ALTERNO B - Sin patrones
    Si ninguna regla supera los umbrales: estado OK con cero hallazgos y el
    mensaje "Todavia no aparece un patron claro en tus datos".

  FLUJO ALTERNO C - Sin consentimiento
    Si el consentimiento no esta aceptado, el sistema no ejecuta el analisis y
    lleva al paciente a CU-04 explicando para que se usaran sus datos.

  FLUJO DE EXCEPCION - Error del motor
    Estado ERROR, se registra en evento_auditoria, el paciente ve el ultimo
    analisis valido y un aviso de reintentar.

  Postcondicion     Existe un registro en 'analisis', N filas en 'hallazgo' y
                    el 'riesgo_diario' de hoy actualizado.

  Req. asociados    RNF-01 (rendimiento), RNF-07 (explicabilidad),
                    RNF-08 (suficiencia de datos)

  Diagrama de secuencia: docs/diagramas/04_secuencia_analisis.puml

REGLAS DE NEGOCIO
-----------------
Restricciones del dominio que el sistema aplica siempre, sin importar desde
que caso de uso se llegue.

  RN-01   Sin consentimiento de analisis aceptado, CU-08 no se ejecuta.
          El consentimiento se guarda con su fecha en perfil_clinico.

  RN-02   SUFICIENCIA DE DATOS. Se necesitan al menos 14 dias de bitacora
          completa y 3 episodios registrados para emitir hallazgos.
          Por debajo de eso el analisis devuelve DATOS_INSUFICIENTES.

  RN-03   UMBRALES DE RELEVANCIA. Una regla solo se presenta si cumple
          soporte >= 0.10, confianza >= 0.60, lift >= 1.20 y tiene como
          maximo 3 items en el antecedente. Se muestran a lo sumo 10
          hallazgos.

  RN-04   NIVEL DE CONFIANZA POR NUMERO DE OBSERVACIONES, no por fuerza de
          la regla:
              ALTA   >= 10 episodios relacionados  y  p < 0.05
              MEDIA  >=  5 episodios relacionados  y  p < 0.10
              BAJA   el resto (con advertencia reforzada)

  RN-05   Un unico registro de bitacora por usuario y fecha. Un episodio se
          ancla automaticamente al registro del dia en que empezo.

  RN-06   Un resumen clinico siempre referencia el analisis que lo produjo.
          Los hallazgos no se editan nunca: se regeneran en una corrida
          nueva, para que cada resultado sea trazable a sus parametros.

  RN-07   El sistema no emite juicios causales ni predictivos. Ningun texto
          mostrado al paciente afirma que un factor causa migrana ni que va a
          tener un episodio.


================================================================================
05. MODELO DE DATOS
================================================================================

17 tablas en PostgreSQL. La decision de diseno mas importante esta en como se
conectan la bitacora y el motor.


LA DECISION DE DISENO CLAVE
---------------------------

Hay dos formas habituales de guardar factores variables. Una tabla EAV
generica (entidad-atributo-valor) es flexible pero dificil de validar y de
entender. Columnas fijas son simples pero obligan a tocar el motor cada vez
que se agrega un factor. Aqui se combinan las dos:

  registro_diario        Columnas fijas, tipadas, con CHECK de rango.
                         La usan la app movil y los serializadores.
                         Un formulario plano, validacion trivial, consultas
                         rapidas. Facil para los integrantes de nivel inicial.

  catalogo_factor        Metadatos: que columna es cada factor, de que tipo,
                         con que unidad.
                         La usa el motor: itera el catalogo y lee cada columna
                         por su nombre. NO tiene los factores escritos a mano.

  regla_discretizacion   Como convertir un valor crudo en un item, MAS la
                         frase en espanol.
                         La usan el discretizador y el explicador. Agregar un
                         factor nuevo es insertar filas, no reescribir el
                         algoritmo.

  POR QUE IMPORTA PARA LA MATERIA
  El campo regla_discretizacion.descripcion_humana (por ejemplo "durmio menos
  de 6 horas") es lo que hace que la explicabilidad sea un DATO y no texto
  incrustado en el codigo. El explicador compone las frases a partir del
  catalogo, asi que la calidad de las explicaciones se puede revisar,
  versionar y probar sin tocar Python.


LAS TABLAS, POR MODULO
----------------------

  M0 - IDENTIDAD
  --------------
  usuario
      Credenciales y datos basicos del paciente.
      Campos: id, email, password_hash, nombre, apellido, fecha_nacimiento,

POR QUE 'hallazgo' CUELGA DE 'analisis' Y NO DEL USUARIO
--------------------------------------------------------
Un hallazgo solo significa algo en el contexto de la corrida que lo produjo:
el periodo, los umbrales y la version del motor.

Si los hallazgos colgaran del usuario, al cambiar un umbral quedarian
mezclados resultados de criterios distintos y no se podria responder "por que
antes salia esto y ahora no".

Con este diseno cada corrida es inmutable y comparable, que es exactamente lo
que se necesita para demostrar en la materia que el motor mejoro entre el
Sprint 2 y el Sprint 3.

================================================================================
06. COMO FUNCIONA EL MOTOR
================================================================================

Seis pasos, cada uno en su propio archivo y con sus propias pruebas. Este es
el corazon del proyecto y donde se concentra el esfuerzo de calidad.


PASO 1 - VENTANA DE RETRASO (lag_dias)
--------------------------------------
Un episodio del dia D rara vez lo causa lo que paso ese mismo dia: lo antecede
lo del dia anterior. Para cada dia se construye una fila que une los factores
de D y de D-1, y se marca si hubo migrana en D.

El retraso es configurable (0, 1 o 2 dias); por defecto es 1.

    fila(D) = factores(D)  U  factores(D-1) prefijados "AYER_"
              +  MIGRANA = SI | NO


PASO 2 - DISCRETIZACION  (discretizador.py)
-------------------------------------------
Apriori necesita items, no numeros. Cada valor crudo se convierte en una
etiqueta usando regla_discretizacion. Un dia que no cumple ninguna regla de un
factor simplemente no aporta ese item.

    horas_sueno       = 5.5  -->  SUENO_BAJO
    estres_percibido  = 4    -->  ESTRES_ALTO
    comidas_omitidas  = 1    -->  COMIDA_OMITIDA
    horas_pantalla    = 3.0  -->  (ningun item)


PASO 3 - REGLAS DE ASOCIACION  (apriori.py)
-------------------------------------------
Con mlxtend se buscan conjuntos frecuentes y se generan reglas. Solo interesan
las que tienen MIGRANA_SI como consecuente. Se descartan antecedentes de mas
de 3 items: una regla de 5 condiciones no es explicable.

    UMBRALES:
      soporte    >= 0.10    el patron aparece en al menos el 10% de los dias
      confianza  >= 0.60    cuando aparece, 6 de cada 10 veces hubo migrana
      lift       >= 1.20    la migrana es 1.2x mas probable que por azar
      n_items    <= 3       antecedente explicable en una frase

    El LIFT es la metrica clave: sin el, un factor que ocurre todos los dias
    (como "uso pantallas") saldria con confianza altisima aunque no tenga
    ninguna relacion real con los episodios.


PASO 4 - ARBOL DE DECISION  (arbol.py)
--------------------------------------
DecisionTreeClassifier con max_depth=3 y min_samples_leaf=5.

No se usa para predecir sino para LEER sus ramas: cada camino raiz->hoja con
clase MIGRANA_SI se traduce a una regla. Aporta combinaciones que Apriori se
pierde por el umbral de soporte, y da la importancia relativa de cada factor.

    SI sueno < 6.5 h  Y  estres >= 4  -->  migrana en 11 de 13 casos (hoja)


PASO 5 - SIGNIFICANCIA  (correlacion.py)
----------------------------------------
Por cada factor se arma la tabla 2x2 (factor si/no x migrana si/no) y se
aplica chi-cuadrado, o test exacto de Fisher cuando alguna celda tiene menos
de 5 casos, que con pocos episodios pasa siempre.

El p-valor evita presentar como patron lo que es ruido de una muestra pequena.

    SUENO_BAJO     chi2 = 8.41,  p = 0.0037  -->  se conserva
    PANTALLA_ALTA  Fisher        p = 0.42    -->  se descarta


PASO 6 - EXPLICACION  (explicador.py)
-------------------------------------
Cada regla superviviente se convierte en una frase construida con las
descripcion_humana del catalogo, mas su evidencia numerica y su nivel de
confianza.

El nivel sale del NUMERO DE OBSERVACIONES, no de la fuerza de la regla: con
pocos datos, un lift alto sigue siendo poco confiable.

    ALTA   >= 10 episodios relacionados  Y  p < 0.05
    MEDIA  >=  5 episodios relacionados  Y  p < 0.10
    BAJA   el resto -> se muestra con advertencia reforzada

NIVEL DE RIESGO DIARIO  (riesgo.py)
-----------------------------------
Al abrir la app, el paciente ve un semaforo del dia. El score suma el lift de
cada hallazgo de confianza ALTA o MEDIA cuyos items esten activos hoy,
normalizado sobre la suma maxima posible.

  NIVEL   SCORE          QUE DICE LA APP
  -----   ------------   ---------------------------------------------------
  BAJO    < 0.33         "Hoy no coinciden tus factores habituales."
  MEDIO   0.33 - 0.66    "Hoy coincide 1 de tus factores frecuentes:
                          dormiste poco."
  ALTO    > 0.66         "Hoy coinciden 2 de tus factores frecuentes:
                          dormiste poco y te saltaste el desayuno."

  El texto NUNCA dice "te va a doler". Describe coincidencias con el historial
  propio del paciente, que es lo unico que los datos sostienen.

DEFINITION OF READY
-------------------
Una historia NO entra a un sprint si no cumple las seis condiciones:

  1. Esta escrita en formato "Como... quiero... para...", con el "para"
     explicando un beneficio real.
  2. Tiene criterios de aceptacion en Gherkin, incluyendo al menos un
     escenario de error.
  3. Esta estimada por el equipo completo con Planning Poker.
  4. Sus dependencias estan identificadas y resueltas o planificadas antes.
  5. Si tiene interfaz, hay un boceto en Figma aprobado por el PO.
  6. Los datos de prueba necesarios existen o estan en el alcance de HU-08.


DEFINITION OF DONE
------------------
Una historia esta terminada cuando pasa las ocho. No hay "hecho al 90%".

  7  Endpoints documentados en OpenAPI y agregados      drf-spectacular

  8  La suite completa pasa: sin regresiones en lo      CI

PRUEBAS DE ORACULO - EL ARGUMENTO CENTRAL DEL PROYECTO
------------------------------------------------------
Estas siete pruebas son la evidencia de que el motor encuentra lo que debe
encontrar. Se siembra un patron conocido en datos sinteticos y se verifica que
el algoritmo lo recupere. Es lo que permite afirmar que el sistema funciona
sin tener pacientes reales.

  O-01  PATRON SIMPLE FUERTE
        Dataset: 120 dias, 20 episodios. SUENO_BAJO precede 16 de 20
                 episodios; aparece en el 10% de los dias sin episodio.
        Esperado: ranking 1, confianza >= 0.70, lift >= 2.0, p < 0.01.

  O-02  PATRON COMBINADO
        Dataset: SUENO_BAJO + COMIDA_OMITIDA juntos preceden el 80% de los
                 episodios; por separado, el 35%.
        Esperado: la regla de 2 items entra en el top-3 y su lift supera al
                  de cada item por separado.

  O-03  FACTOR DE RUIDO
        Dataset: PANTALLA_ALTA distribuida uniformemente, sin relacion con
                 los episodios.
        Esperado: lift aproximadamente 1.0 -> filtrada. No aparece en ningun
                  hallazgo.

  O-04  DATOS INSUFICIENTES
        Dataset: 10 dias de bitacora, 1 episodio.
        Esperado: estado DATOS_INSUFICIENTES, cero hallazgos, mensaje con lo
                  que falta.

  O-05  SIN PATRON REAL
        Dataset: 90 dias, 30 episodios, todos los factores aleatorios.
        Esperado: ningun hallazgo con nivel de confianza ALTA.

  O-06  MUESTRA DESBALANCEADA
        Dataset: 200 dias con solo 3 episodios, patron presente en los 3.
        Esperado: el hallazgo aparece pero marcado BAJA. Lift alto con n
                  pequeno no es confianza alta.

  O-07  RENDIMIENTO
        Dataset: 365 dias, 60 episodios, 12 factores.
        Esperado: analisis completo en menos de 3 segundos.


  COMO SE PRESENTA ESTO EN LA DEFENSA
  O-03, O-05 y O-06 son las mas valiosas, y son las que un equipo sin
  formacion en calidad no escribiria. Demuestran que el sistema SABE CALLARSE:
  que no inventa patrones cuando no los hay, y que reconoce cuando tiene pocos
  datos. En un sistema de salud, el falso positivo es peor que el silencio.

GESTION DE RIESGOS
------------------

  R1 - EL MOTOR NO ENCUENTRA PATRONES EN DATOS REALES
       porque 9 semanas no alcanzan para acumular historial
       Probabilidad: ALTA      Impacto: ALTO
       Mitigacion: la demo se hace con datasets sinteticos de HU-08 y con las
       pruebas de oraculo. Los datos reales del equipo son complemento, no la
       base de la validacion. ESTO SE ACUERDA CON EL DOCENTE EN LA SEMANA 1.

  R2 - LOS INTEGRANTES DE NIVEL INICIAL SE BLOQUEAN
       y el trabajo se concentra en dos personas
       Probabilidad: MEDIA     Impacto: ALTO
       Mitigacion: emparejamiento fijo por frente, revision cruzada
       obligatoria de PR, y roles con propiedad real (PO y QA) que no dependen
       del nivel tecnico. Se vigila en cada Retro.

  R3 - APRIORI DEVUELVE CIENTOS DE REGLAS
       y la pantalla es ilegible
       Probabilidad: MEDIA     Impacto: MEDIO
       Mitigacion: umbrales estrictos desde el primer dia (lift >= 1.2, max. 3
       items), deduplicacion de reglas que se implican entre si y tope de 10
       hallazgos mostrados.

  R4 - SE PRESENTAN HALLAZGOS FALSOS
       por muestras pequenas
       Probabilidad: MEDIA     Impacto: ALTO
       Mitigacion: umbral duro de suficiencia (RN-02), p-valor obligatorio,
       nivel de confianza por numero de observaciones y la advertencia
       permanente de no causalidad. Cubierto por O-04, O-05 y O-06.

  R5 - FLUTTER CONSUME MAS TIEMPO DEL ESTIMADO
       en el Sprint 1
       Probabilidad: MEDIA     Impacto: MEDIO
       Mitigacion: el backend avanza en paralelo y no depende del movil. Si
       hace falta, el Sprint 1 cierra con las pantallas de captura funcionando
       y sin pulir visualmente.

  R6 - MANEJO DE DATOS DE SALUD SIN BASE LEGAL CLARA
       Probabilidad: BAJA      Impacto: ALTO
       Mitigacion: consentimiento explicito con fecha (perfil_clinico), tokens
       en almacen cifrado, auditoria de accesos, y ningun dato identificable
       en logs ni en los datasets de prueba.

' ===================== M0 : IDENTIDAD =====================
entity "usuario" as usuario {
  * id : BIGSERIAL <<PK>>
  --
  * email : VARCHAR(150) <<UQ>>
  * password_hash : VARCHAR(255)
  * nombre : VARCHAR(80)
  * apellido : VARCHAR(80)
  fecha_nacimiento : DATE
  sexo : ENUM(F, M, OTRO, NS)
  zona_horaria : VARCHAR(40)
  * fecha_registro : TIMESTAMPTZ
  ultimo_acceso : TIMESTAMPTZ
  * activo : BOOLEAN
}

entity "perfil_clinico" as perfil {
  * id : BIGSERIAL <<PK>>
  --
  * usuario_id : BIGINT <<FK>> <<UQ>>
  anios_con_migrana : SMALLINT

  tipo_migrana : ENUM(CON_AURA, SIN_AURA, CRONICA, DESCONOCIDA)
  medicacion_habitual : TEXT
  ciclo_menstrual_aplica : BOOLEAN
  * consentimiento_analisis : BOOLEAN
  fecha_consentimiento : TIMESTAMPTZ
}

' ========== M4 : CATALOGOS Y METADATOS DEL MOTOR ==========
entity "catalogo_factor" as factor {
  * id : SMALLSERIAL <<PK>>
  --
  * codigo : VARCHAR(30) <<UQ>>
  * nombre_campo : VARCHAR(40)
  * etiqueta : VARCHAR(80)
  * tipo_dato : ENUM(NUMERICO, ORDINAL, BOOLEANO, CATEGORICO)
  unidad : VARCHAR(20)
  valor_min : NUMERIC(6,2)
  valor_max : NUMERIC(6,2)
  * aplica_lag : BOOLEAN
  * activo : BOOLEAN
  * orden : SMALLINT
}

entity "regla_discretizacion" as regla {
  * id : SMALLSERIAL <<PK>>
  --
  * factor_id : SMALLINT <<FK>>
  * etiqueta_item : VARCHAR(40)
  * operador : ENUM(LT, LTE, BETWEEN, EQ, GTE, GT, IN)
  valor_min : NUMERIC(6,2)
  valor_max : NUMERIC(6,2)
  valor_texto : VARCHAR(40)
  * descripcion_humana : VARCHAR(120)
  * orden : SMALLINT
  --
  UQ(factor_id, etiqueta_item)
}

entity "alimento" as alimento {
  * id : SMALLSERIAL <<PK>>
  --
  * codigo : VARCHAR(30) <<UQ>>
  * nombre : VARCHAR(60)
  * grupo : ENUM(LACTEO, EMBUTIDO, CHOCOLATE, CAFEINA,
      ALCOHOL, GLUTAMATO, CITRICO, EDULCORANTE, OTRO)
  * activo : BOOLEAN
}

entity "sintoma" as sintoma {
  * id : SMALLSERIAL <<PK>>
  --
  * codigo : VARCHAR(30) <<UQ>>
  * nombre : VARCHAR(60)
  * activo : BOOLEAN
}

' ===================== M1 : CAPTURA =====================
entity "registro_diario" as diario {
  * id : BIGSERIAL <<PK>>
  --
  * usuario_id : BIGINT <<FK>>
  * fecha : DATE
  horas_sueno : NUMERIC(4,2)
  calidad_sueno : SMALLINT      /* 1..5 */
  hidratacion : ENUM(BAJA, MEDIA, ALTA)
  comidas_omitidas : SMALLINT   /* 0..3 */
  estres_percibido : SMALLINT   /* 1..5 */
  horas_pantalla : NUMERIC(4,2)
  minutos_actividad : SMALLINT
  cafeina_tazas : SMALLINT
  consumo_alcohol : BOOLEAN
  fase_ciclo : ENUM(NO_APLICA, MENSTRUACION, FOLICULAR,
      OVULACION, LUTEA)
  * completado : BOOLEAN
  * origen : ENUM(MANUAL, SINTETICO, IMPORTADO)
  * creado_en : TIMESTAMPTZ
  * actualizado_en : TIMESTAMPTZ
  --
  UQ(usuario_id, fecha)
  IDX(usuario_id, fecha DESC)
}

entity "registro_alimento" as regali {
  * id : BIGSERIAL <<PK>>
  --
  * registro_diario_id : BIGINT <<FK>>
  * alimento_id : SMALLINT <<FK>>
  porciones : SMALLINT
  --
  UQ(registro_diario_id, alimento_id)
}

entity "episodio_migrana" as episodio {
  * id : BIGSERIAL <<PK>>
  --
  * usuario_id : BIGINT <<FK>>
  registro_diario_id : BIGINT <<FK>>   /* NULL */
  * inicio : TIMESTAMPTZ
  fin : TIMESTAMPTZ
  duracion_min : INTEGER
  * intensidad_eva : SMALLINT           /* 1..10 */
  localizacion : ENUM(UNILATERAL_IZQ, UNILATERAL_DER,
      BILATERAL, OCCIPITAL, DIFUSA)
  tuvo_aura : BOOLEAN
  medicacion_tomada : VARCHAR(120)
  minutos_hasta_alivio : INTEGER
  alivio_percibido : SMALLINT           /* 0..10 */
  limito_actividad : BOOLEAN
  notas : TEXT
  * creado_en : TIMESTAMPTZ
  --
  IDX(usuario_id, inicio DESC)
}

entity "episodio_sintoma" as episin {
  * id : BIGSERIAL <<PK>>
  --
  * episodio_id : BIGINT <<FK>>
  * sintoma_id : SMALLINT <<FK>>
  --
  UQ(episodio_id, sintoma_id)
}

' ===================== M2 : ANALISIS =====================
entity "analisis" as analisis {
  * id : BIGSERIAL <<PK>>
  --
  * usuario_id : BIGINT <<FK>>
  * ejecutado_en : TIMESTAMPTZ
  * periodo_inicio : DATE
  * periodo_fin : DATE
  * dias_analizados : INTEGER
  * episodios_analizados : INTEGER
  * lag_dias : SMALLINT                 /* 0..2 */
  * version_motor : VARCHAR(20)
  parametros : JSONB  /* soporte_min, confianza_min,
                         lift_min, profundidad_max */
  * estado : ENUM(OK, DATOS_INSUFICIENTES, ERROR)
  mensaje_estado : VARCHAR(200)
  duracion_ms : INTEGER
  --
  IDX(usuario_id, ejecutado_en DESC)
}

entity "hallazgo" as hallazgo {
  * id : BIGSERIAL <<PK>>
  --
  * analisis_id : BIGINT <<FK>>
  * tipo : ENUM(ASOCIACION, ARBOL, CORRELACION, FRECUENCIA)
  * antecedente : JSONB  /* ["SUENO_BAJO", "DESAYUNO_OMITIDO"] */
  soporte : NUMERIC(5,4)
  confianza : NUMERIC(5,4)
  lift : NUMERIC(6,3)
  p_valor : NUMERIC(6,5)
  * episodios_relacionados : INTEGER
  * total_episodios : INTEGER
  * nivel_confianza : ENUM(ALTA, MEDIA, BAJA)
  * texto_explicacion : TEXT
  * ranking : SMALLINT
}

entity "valoracion_hallazgo" as valoracion {
  * id : BIGSERIAL <<PK>>
  --
  * hallazgo_id : BIGINT <<FK>>
  * usuario_id : BIGINT <<FK>>
  * util : BOOLEAN
  comentario : VARCHAR(300)
  * creado_en : TIMESTAMPTZ
  --
  UQ(hallazgo_id, usuario_id)
}

entity "riesgo_diario" as riesgo {
  * id : BIGSERIAL <<PK>>
  --
  * usuario_id : BIGINT <<FK>>
  * fecha : DATE
  * nivel : ENUM(BAJO, MEDIO, ALTO)
  * score : NUMERIC(5,2)
  factores_activos : JSONB
  analisis_id : BIGINT <<FK>>
  * calculado_en : TIMESTAMPTZ
  --
  UQ(usuario_id, fecha)
}

  * periodo_fin : DATE
  * resumen : TEXT
  * formato : ENUM(PDF, TEXTO)
  hash_contenido : VARCHAR(64)
  veces_compartido : INTEGER
}

  * id : BIGSERIAL <<PK>>
  --
  usuario_id : BIGINT <<FK>>

  * entidad : VARCHAR(40)
  entidad_id : BIGINT
  detalle : JSONB
  ip : INET
  * ocurrido_en : TIMESTAMPTZ
}
